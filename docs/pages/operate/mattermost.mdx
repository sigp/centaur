# Mattermost

Centaur's Mattermost ingress connects to Mattermost over its websocket API and
forwards allowed channel messages to `api-rs`. It creates one Centaur principal
per Mattermost channel, including direct-message channels. Direct messages are
denied by default and can be enabled for one-to-one channels only; group
messages remain denied.

## Create the Mattermost bot account

A Mattermost administrator must create the bot account:

1. Open **System Console → Integrations → Bot Accounts**.
2. Choose **Add Bot Account**, set the username to the value used by
   `mattermostbot.userName` (normally `centaur`), and save it.
3. Copy the bot token when Mattermost displays it. If it is no longer
   available, regenerate the token and update the Kubernetes Secret.
4. Add the bot account to every public or private channel where it should
   operate. It must have permission to read posts and post replies.

For acknowledgement and steering reactions, the bot account also needs
permission to add and remove reactions in each channel. Mattermost channel IDs
are 26-character lowercase alphanumeric strings; use the ID, not the channel
name, in channel-keyed settings.

The allowlist uses Mattermost **team IDs or names**. As an administrator or
with a suitable Mattermost token, list teams with the Mattermost API:

```sh
curl -sS -H "Authorization: Bearer $MATTERMOST_BOT_TOKEN" \
  "$MATTERMOST_BASE_URL/api/v4/teams" | jq -r '.[] | [.id, .name] | @tsv'
```

Use either the IDs or the names for the teams that Centaur may serve. The bot
ignores all messages until at least one allowlist entry is present. If api-rs
rejects a session because its Mattermost principal is not admitted, the bot
posts one short `Centaur isn't enabled for this channel yet.` reply.

## Configure the chart

Mattermost is off by default. Add a values overlay such as:

```yaml
mattermostbot:
  enabled: true
  userName: centaur
  serverUrl: https://mattermost.example.com
  teamAllowlist: "TEAM_ID_1 TEAM_NAME_2"
  extraEnv:
    MATTERMOSTBOT_DIRECT_MESSAGES: "true"
  serverEgress:
    port: 443
    # Optional: restrict the server destination. NetworkPolicy cannot match
    # hostnames, so use the server's stable CIDR(s).
    cidrs:
      - 203.0.113.10/32
```

`serverUrl` is required when `mattermostbot.enabled` is true. The default
`serverEgress` permits TCP 443 to any destination, like the Discord ingress.
Set `serverEgress.port` for a Mattermost server on another port. For an
in-cluster Mattermost deployment, select its pods instead:

```yaml
mattermostbot:
  serverEgress:
    port: 8065
    podSelector:
      app.kubernetes.io/name: mattermost
    namespace: mattermost
```

Use either destination CIDRs or an in-cluster pod selector when you need to
restrict egress. The chart-wide NetworkPolicy already permits DNS. The
Mattermost policy also permits the api-rs service and the configured Postgres
state store, and admits health probes and annotation-based metric scrapes on
port 3001. If proactivity or the `llm` message-override strategy is enabled,
it adds TCP 443 egress for the configured OpenAI-compatible endpoint.

## Expose workflow and slash-command endpoints

The optional Mattermost Ingress exposes only the `/api/mattermost` prefix on
the bot's port `3001`; health and metrics remain private. Set `publicUrl` to
the HTTPS origin reachable by Mattermost, or leave it empty to derive
`https://<ingress.host>` when the chart's ingress is enabled with a host. Add
the ingress controller namespace to `networkPolicy.ingressSourceNamespaces`.

```yaml
mattermostbot:
  publicUrl: https://centaur-mm.example.com
  ingress:
    enabled: true
    className: nginx
    host: centaur-mm.example.com
    tls:
      - hosts: [centaur-mm.example.com]
        secretName: centaur-mm-tls
  slashCommands:
    workflows: [deploy, investigate]
```

Create the command under **Product menu → Integrations → Slash Commands → Add
Slash Command**. If **Integrations** is missing, a System Admin enables custom
slash commands under **System Console → Integrations → Integration
Management**. Configure:

- Command trigger word: `centaur`
- Request URL: `<publicUrl>/api/mattermost/commands`
- Request method: `POST`

Put the token Mattermost generates in the infra Secret as
`MATTERMOSTBOT_SLASH_COMMAND_TOKENS`; do not put it in a values file. The
bootstrap script accepts the same-named shell variable and rotates it on each
run.

`/centaur help` lists commands. `/centaur run <workflow> [JSON object]` starts one
of the names in `mattermostbot.slashCommands.workflows`; the optional JSON object
is passed as workflow input. Any other text is a prompt: the bot posts
`@<user> asked: <prompt>` and answers in that post's thread, as if the user had
mentioned it, so inline flags work too.

Typed in a thread's reply box, a command stays in that thread: a prompt joins
the thread's conversation like a mention there (steering a running turn),
`run` posts its start notice in the thread and gives the workflow that thread,
and `/centaur stop` interrupts the thread's running turn, as `@<bot> stop` does.
Typed in the channel, `/centaur stop` only explains that it needs a thread.

Workflow messages can include interactive buttons. Mattermost sends each click
to the bot's `/api/mattermost/actions`; the bot checks the team, channel and
post, and api-rs verifies the button's signature before starting the run. No
callback secret is configured separately.

The chart renders `MATTERMOST_BASE_URL` and `MATTERMOST_BOT_TOKEN` into api-rs
when the bot is enabled, plus `MATTERMOST_WORKFLOW_ACTIONS_URL` when `publicUrl`
is set or the ingress fallback applies.

## Provide secrets and deploy

The bootstrap script accepts the token directly from the shell. It overwrites
`MATTERMOST_BOT_TOKEN` on every run so rotation is explicit, and generates
`MATTERMOSTBOT_API_KEY` once when that key is absent:

```sh
export MATTERMOST_BOT_TOKEN='paste-the-token-in-your-shell'
CENTAUR_NAMESPACE=centaur just bootstrap-secrets
```

Do not commit the token or put it in a values file. Production deployments can
provide these keys in the Secret named by `secretManager.existingSecretName`:

- `MATTERMOST_BOT_TOKEN`
- `MATTERMOSTBOT_API_KEY`
- `MATTERMOSTBOT_SLASH_COMMAND_TOKENS` (when slash commands are enabled)
- `DATABASE_URL` (the Chat SDK state store is rendered as
  `MATTERMOSTBOT_DATABASE_URL`)

For the `sigp/centaur` fork, the fork release workflow publishes the chart to
`oci://ghcr.io/sigp/centaur/charts/centaur:<version>-sigp-<sha7>` and stamps
each chart-deployable project image to
`ghcr.io/sigp/centaur/<image>:<commit sha>`. The controller and bundled
PostgreSQL keep their upstream/system image references.

The workflow builds `centaur-api-rs`, `centaur-console`, `centaur-agent`, and
`centaur-mattermostbot`. It mirrors `centaur-iron-proxy`,
`centaur-proxy-sync`, `centaur-token-broker`, `centaur-company-context`,
`centaur-slackbotv2`, `centaur-linearbot`, `centaur-githubbot`,
`centaur-discordbot`, and `centaur-teamsbot` from the fork's upstream
merge-base. Select the OCI chart version and apply the Mattermost values
overlay; the release chart already contains the immutable image references:

```sh
COMMIT_SHA=0123456789abcdef0123456789abcdef01234567
CHART_VERSION=0.1.205
helm upgrade --install centaur \
  oci://ghcr.io/sigp/centaur/charts/centaur \
  --version "${CHART_VERSION}-sigp-${COMMIT_SHA::7}" \
  --namespace centaur --create-namespace \
  -f mattermost-values.yaml
```

For an upstream checkout, the local chart command below is sufficient.

Then deploy the chart with the Mattermost values overlay:

```sh
helm upgrade --install centaur contrib/chart \
  --namespace centaur --create-namespace \
  -f contrib/chart/values.yaml \
  -f mattermost-values.yaml
```

Check the singleton and its connection health with the commands below. The pod
is ready only while its Mattermost websocket is connected (`/health`).

```sh
kubectl -n centaur get deployment,service,pod -l app.kubernetes.io/component=mattermostbot
kubectl -n centaur logs -l app.kubernetes.io/component=mattermostbot --tail=50
```

The deployment has exactly one replica and uses `Recreate`. Two pods using the
same Mattermost bot token would each receive every websocket event.

## Stop a turn and choose a harness

Mention the bot and send a stop request to interrupt the active execution:

```text
@centaur stop
@centaur cancel this turn
```

The stop parser also accepts `kill`, `end`, and common inflected forms, with
optional words such as `please`, `now`, or `the run`. A stop request is only
recognized when it mentions the bot; it does not accidentally treat an
ordinary post containing the word “stop” as a command.

The same mention can carry inline controls. Flags are removed before the post
reaches the harness:

- `--claude` or `--claude-code`, `--codex`, `--nanocodex`, `--amp`, `--pi`,
  and `--omp` select a harness.
- `--bedrock`, `--meta`, or `--provider <name>` select a Codex provider.
- `--persona <id>` (or `--persona=<id>`) selects the persona when the thread
  session is created.
- `--model <name>` (or `--model=<name>`) selects a model, and
  `--fable`, `--opus`, `--sonnet`, and `--haiku` are Claude model shortcuts.
- `-rsn <effort>` (or `-rsn=<effort>`) sets per-turn reasoning effort.

Harness, model, and provider choices stick to the Mattermost thread. An
explicit harness flag on a thread pinned to another harness restarts that
thread on the requested harness. The deployment default is Codex unless
`sandbox.harnessEngine` or `MATTERMOSTBOT_DEFAULT_HARNESS` changes it.
`MATTERMOSTBOT_ENABLED_HARNESSES`, supplied through `mattermostbot.extraEnv`,
can restrict the harnesses available to inline flags and channel defaults.

## Channel defaults and reactions

`mattermostbot.channelDefaults` is a JSON object keyed by a 26-character
Mattermost channel ID. Each value may contain `persona`, `harness`, `model`,
`provider`, and `reasoning`, using the same vocabulary as the inline flags:

```yaml
mattermostbot:
  channelDefaults:
    0123456789abcdefghijklmnop:
      harness: claude
      model: opus
      reasoning: high
```

A channel default applies when a post has no explicit or sticky thread choice,
below an explicit choice and above the deployment default. A persona applies
when a session is created. Use an empty object to leave channel defaults
disabled.

The chart enables acknowledgement reactions by default:
`ackReactionEnabled: true` uses the Mattermost `eyes` emoji after a mentioned
post starts a turn and removes it after the answer is posted.
`steeringReactionEnabled: false` can be enabled to use
`hourglass_flowing_sand` on accepted follow-ups while a turn is running.
Set `ackReaction` and `steeringReaction` to other Mattermost emoji names when
needed. The bot must be allowed to add reactions; if Mattermost rejects a
reaction, that reaction kind is disabled for the running process and the bot
logs the failure once.

## Mention gating and proactive replies

Mattermost operation is mention-gated. A post that does not mention the bot
never reaches a running turn on its own; the next mention in the thread brings
it in as context. A mentioned follow-up during a turn steers that turn.

With proactivity enabled, an unmentioned follow-up in a thread where the bot
was mentioned (or answered on a rule match) goes to a classifier, and an
accepted post is handled like a mentioned follow-up: it starts a turn or
steers the running one. A classifier failure or timeout means no reply. Only a
mention can stop a turn, and a stop silences proactive replies in its thread
until the next mention.

Proactivity and the `llm` override strategy both call an OpenAI-compatible
Decisions API endpoint. Enable proactivity with:

```yaml
mattermostbot:
  proactivity:
    enabled: true
    classifier: openai
    model: gpt-6-luna
    timeoutMs: 2000
    debounceMs: 500
```

Set `messageOverridesStrategy.mode: llm` to also read harness, model, and
reasoning requests from plain language, not only from flags.

`OPENAI_API_KEY` comes from the infra Secret. For a separate key, set
`MATTERMOSTBOT_MESSAGE_OVERRIDES_OPENAI_API_KEY` or
`MATTERMOSTBOT_PROACTIVITY_OPENAI_API_KEY` through `mattermostbot.extraEnv`.
The matching `openaiBaseUrl` values select an OpenAI-compatible endpoint.
`debounceMs` waits for a quiet period before classifying an idle-thread burst;
zero classifies each post immediately.

Operator rules can make a channel proactive without a prior mention. Rules
are arrays of at most 20 uniquely named entries with `when` and optional
`context` fields:

```yaml
mattermostbot:
  proactivity:
    enabled: true
    defaultRules:
      - name: incident
        when: Questions about an active incident in a service we own.
        context: Check dashboards and recent deploys before replying.
    channelRules:
      0123456789abcdefghijklmnop: []
```

`defaultRules` applies to every channel. A `channelRules` entry replaces it
for that channel; an empty list disables rule matching there. A matched rule
can start a reply thread under a top-level post (`root_id` is the post ID),
and its context is sent on the first execution it starts in that thread (and
again after a harness restart).
The chart mounts `default.json` and `<channelId>.json` from a ConfigMap and
sets `MATTERMOSTBOT_PROACTIVITY_RULES_DIR` automatically when rules are
configured.

## Model footer and metrics

Set `responseMetadataMode` to `first` (the reply to the thread's first turn),
`always` (every reply), or `never` (no replies). When enabled, the trailing
Mattermost markdown line shows the effective model, harness, and reasoning
effort. If it would exceed `MATTERMOSTBOT_MAX_POST_CHARS`, the bot posts the
footer as a short reply instead. `responseServiceTierEnabled` includes the
Codex service tier in the footer when one is available. Model values mirrored
from `sandbox.extraEnv` (`CLAUDE_MODEL`, `CODEX_MODEL`,
`CODEX_MODEL_REASONING_EFFORT`, `CENTAUR_PI_MODEL`, and `CENTAUR_OMP_MODEL`)
are overridden by matching `mattermostbot.extraEnv` entries.

Mattermostbot always exposes Prometheus text at `GET /metrics` on port `3001`.
The chart's `mattermostbot.metrics.scrapeAnnotations` (default `true`) adds
`prometheus.io/scrape`, `prometheus.io/path`, and `prometheus.io/port`
annotations; `metrics.path` changes the path and `metrics.annotations` adds or
overrides annotation values.

## Supported surface

The first Mattermost integration deliberately has a narrow surface:

- Channel posts and thread replies in allowlisted teams are supported.
- Centaur uses the channel ID (and, for a thread, the root post ID) as the
  thread identity, so replies stay in the originating Mattermost thread.
- Direct messages and group-message channels are denied, even if the bot is
  added to them.
- There is one bot replica by design. Do not add an HPA or a second pod.
